# Claude Code: holistic integration from first principles

**Status: CONVERGED (round 4 + coordinator final pass + final evidence/consistency audits, both PASS on this text).** Commissioned by Jeff after the extraction plan (docs/plans/claude-code-inline-extraction.md, landed `ead0fd6`) exposed how much of thatch's shape is opencode-accommodation rather than design. Framing, verbatim intent: treat Claude Code as a **completely new harness** we want to support - not a port-the-gaps exercise. **Implementation HELD**; this doc is the artifact until Jeff approves.

## Goal

Design Claude Code support from the feature list outward: what each feature is FOR (essential semantics), what exists only to accommodate opencode v1/v2 SDK quirks, what genuinely cannot be supported on Claude Code, and what code structure a first-class dual-plugin setup (opencode plugin + Claude Code plugin over one shared core) needs. Every piece must justify itself against EXTERNAL USERS' pain (setup drift, silently-missing features), not Jeff's workflow - Jeff does not use Claude Code.

## Background

### The Claude Code surface (verified against live docs 2026-11-04)

Claude Code has an in-process plugin surface ("mods", v2.1.287+, per mods/overview.md and the CHANGELOG "Added Claude Mods"): a plugin's `register.js` exports `register(on)` and handlers run INSIDE Claude Code as middleware. Events (mods/events.md): `tool.call` (observe/rewrite/answer any tool call, including subagent and MCP calls), `tool.check` (permission decisions), `prompt.submit` (rewrite the prompt, or append Claude-only context via `e.context`), `turn.start`/`turn.step`/`turn.complete` (per-request hooks; `turn.complete` carries `isAborted`, `answer`, `durationMs`, `usage`), `settings.read`, `session.receive`/`session.send` (cross-session messaging, observe/consume), `session.start` (once per mod load, before the first prompt, and again after a mod reload - NOT after `/clear`, `/resume`, `/branch`, or compaction; the post-compaction re-fire belongs to the settings-hook `SessionStart` with matcher `compact`, which mods reach as `classic.SessionStart`), `session.end` (fires when a session ends AND on `/clear`, `/resume`, `/branch`, with an `e.reason` field and a 1.5-second total budget), `command.run`, and `classic.*` (every settings-hook event with the same JSON payloads, `session_id` + `transcript_path` included). Mods API (`$`): `$.command.register` (commands that run functions with no Claude turn; `immediate: true` runs while Claude works), `$.tool.register` (tools surfaced as `mcp__<plugin>__<name>`), `$.agent.spawn`/`$.agent.list` (subagent dispatch and listing), `$.model.complete`/`fork`, `$.prompt.submit` (start a turn from a background job - the proactive wake channel MCP hosts never had), `$.clock.every`/`after` (timers outside event time budgets), `$.fs`/`$.process`/`$.http`, `$.store` (JSON key-value, kept between sessions, 4 MiB, shared by every session on the machine), `$.ui.status`/`toast`/`log`/`notify`/`ask`, `$.session.id`/`send`/`messages`/`usage`/`compact`, `$.mcp.connect`/`call` (connect servers listed in the plugin's own manifest). **Load-bearing constraint, verbatim:** "The hooks module itself has no Node.js APIs, no timer globals such as `setTimeout`, and no network or file access of its own" - everything goes through the capability-mediated `$`. A plugin bundles the mod, settings hooks, skills, commands, subagent definitions, AND an MCP server in one installable unit (marketplace, `/plugin install name@marketplace`).

Failed mod hooks are skipped mid-chain (events.md) - every blocking hook needs a `.catch` handler with an explicit fail-open or fail-closed decision. Enterprise note: the built-in `cc-plugin-sec-default` guard can bypass user-mod hooks where managed settings apply.

### Intent history (why today's integration looks the way it does)

- The CC integration was born `bafab9c` (2026-07-07) as a hand-rolled stdio JSON-RPC MCP server plus settings hooks - the only surface at the time. Mods (v2.1.287) did not exist; no commit, doc, or issue records ANY in-process-plugin discussion before November 2026 (git grep across all revisions: zero). The stdio+hooks choice was not a rejection of something better.
- HostCapabilities (src/capabilities.ts) was introduced `b57fdc7` (2026-09-24) as an explicitly v1/v2-scoped seam: "the plugin-lifecycle operations the shared runtime needs from **whatever opencode version hosts it**". It was never intended as host-neutral. No earlier artifact proposes widening it to a third host.
- The `opencodeOnly` tool fence (0d2a56e, 2026-09-04) was a single-tool decision; watch tools were fenced 03daf65 (2026-09-08) for a recorded reason - "MCP hosts have no poller and no proactive-prompt channel" - with exactly one recorded future-opening idea: "a future CLI daemon could close this gap" (docs/dev/features/watchers.md:311). Mods are a different opening of the same gap.
- No prior holistic-CC effort exists in history. The superseded approach is the model-driven sub-agent dispatch handshake (`0dafeeb`), retired by the landed inline-extraction plan.
- Regime vocabulary used below: the **settings-hook regime** is today's main-branch behavior (dispatch-handshake nudges + `6ea9967`'s deny set), plus the **inline bridge** of `ead0fd6` - that plan is LANDED AS A DOC but its implementation is HELD, so until it is implemented the settings-hook regime still dispatches sub-agents. The **plugin regime** is this plan's target.

## Mandate 2: the concept map (essential semantics vs opencode-quirk accommodation)

Per feature: what it is FOR, the quirk-accommodation parts, and the disposition in the plugin regime. (Full inventory citations in the research notes; every claim here verified against repo files at HEAD.)

1. **Extraction** - FOR: capture durable facts without model cooperation. Essential: the interaction buffer, meta-tool deny set, MEMORY_SAVED_MARKER gate, claim-scoped completion. Quirk accommodation: `unwrapExecuteThatchCalls` (src/extraction.ts:152 - exists because opencode has an `execute` meta-tool whose inner calls bypass per-tool hooks); the plugin-created child session + session-id interpolation + childToParent + the stranded-child sweep (exist because opencode has a session-creation API and a history of model-copied-ID mis-targeting); the file-backed queue + missed-nudge escalation (exist because settings hooks are fresh processes). **Disposition (plugin regime):** the buffer and queue live in the BUNDLED SERVER (full Node, owns file I/O, survives mod reload - module state is wiped on reload per mods docs); the mod calls it per `tool.call` and triggers extraction at `turn.complete`; no child sessions (no session-creation API - extraction runs inline in the parent via context injection, the ead0fd6 pattern). The file-backed queue STAYS as the durable backing on this path - mod reloads and server restarts lose nothing. `unwrapExecuteThatchCalls` is opencode-only and stays there.
2. **Nudge pipeline** - FOR: inject recall/prediction/behavior/write context at the right moment. Essential: tiers, thresholds, one shared embedding, snapshot footers, `db.search`-not-`recall`. Quirk accommodation: the ENTIRE delivery layer - v1 synthetic noReply parts, v2 `pendingInjections` text-equality binding (documented unverified replay edges), the synthetic-only skip guard, toast routing, `--json`/`additional_context` wrapping, five prompt-field spellings (the five fallbacks `flush-tools` tries per payload, bin/thatch:1403-1412). **Disposition:** delivery collapses to `prompt.submit` returning `e.context` appended for Claude. The stage COMPUTATION stays single-sourced: the bundled server exposes a stage tool (the sideband's role, reborn as `$.mcp.call`), so the thresholds and escalation ladder exist exactly once and both regimes consume them (the settings-hook regime via flush-tools stdout, the plugin regime via `e.context`).
3. **Cross-session chat** - FOR: sessions on one machine coordinate through a shared inbox without routing through the human. Essential: the DB store, assigned never-reused names, heartbeat/staleness, tombstones, dedupe, rate caps, injection hygiene. Quirk accommodation: the ppid map + CLAUDE_CODE_SESSION_ID + claimed-`as` identity stack and `mcp_<hash>` derived IDs (exist because MCP tool calls carry no session context); the poller + `guardDelivery` (opencode has no push channel and surfaces failed prompts as toasts); transcript echo bubbles (v2-gated); os-args `-s`/`-c` archaeology; the machinery-session guard (extraction-child corpses). **Disposition:** the plugin regime passes the CC session id with every `$.mcp.call` (the mod reads it via `$.session.id()` - verified in the mods reference), so chat tools resolve identity in one hop; CC-to-CC delivery goes native (`session.send`/`session.receive`); CROSS-HOST mail (opencode sessions cannot `$.session.send`) keeps the DB as the inbox with a mod poll cadence (`$.clock.every`), since `session.receive` fires only for host-native messaging; `$.prompt.submit` is the wake. Continuation adoption (transcript-tail walk) STAYS - CC forks session ids on resume, and `session.end` fires on `/clear`, `/resume`, and `/branch` too (`e.reason`), so cleanup and identity decisions branch on the reason, never on the event alone. The identity stack survives only in the settings-hook regime.
4. **Session lifecycle** - FOR: child cleanup, start reminders, wrap-up resolution, self-healing. Essential: claim-scoped cleanup, greenlight protocol, hygiene heartbeat. Quirk accommodation: bus-event dispatch + v2 directory filters, the stranded-session sweep (v2 promise-domain gaps + plugin-created corpses), `runtime_state` journal/rehydration (v2 auto-reload), legacy TUI command routes. **Disposition:** no plugin-created sessions means no corpses, no journal, no sweep. `classic.SessionStart` (including the post-compaction re-fire with matcher `compact`) carries the reminder + hygiene heartbeat; `session.end` carries child/watcher cleanup, branched on `e.reason` (it fires on `/clear`, `/resume`, and `/branch` too, not just real ends) and inside its 1.5-second budget.
5. **Commands** - FOR: user-invoked workflows + greenlight-gated wrap-ups. Essential: prompt cores single-sourced with nudges, artifacts-as-source, parity guard. Quirk accommodation: file sync + file/code collision cleanup, the three-variant `$ARGUMENTS` substitute matrix, load-order invisibility. **Disposition:** mod commands are registrations, not files; cores stay single-sourced in src/commands.ts and are rendered into the mod's registration code at plugin build time.
6. **Skills** - FOR: install SKILL.md workflow files. Essential: the shared/opencode-only split, content-compare install, stale cleanup, single-sourced specialist roster. Quirk accommodation: install trigger and the coordinator exclusion (can't-list #4). **Disposition:** bundled with the plugin on the plugin regime; the coordinator moves to shared (Step E); `thatch-coordination` stays v2/opencode-only - a NAMED documented gap like session tabs (it rides the rpc-event TUI bridge).
7. **Watchers** - FOR: poll external sources, prompt the session when something happens. Essential: registry semantics, pointer-only notifications, delivery gating, one-shot/TTL. Quirk accommodation: in-memory registry + dormant journaling (the registering process must survive to deliver; v2 reload), 404-class death detection, and the opencodeOnly fence. **Disposition:** the registry moves to the DB via the bundled server (shared across sessions - fixing today's one-session-lifetime); the mod's `$.clock.every` is the poller cadence with ownership keyed by session; `session.end` is death detection; `$.prompt.submit` is delivery. Watch tools become registerable on CC for the first time.
8. **Alerts** - FOR: out-of-band user notification on pause/error/round-done. Essential: the verdict state machine fed by tool-side bookkeeping + round shape. Quirk accommodation: opencode-only because the event feed was; idle-marker message archaeology. **Disposition:** `turn.complete` (`isAborted`, duration, usage) + `classic.PermissionRequest` feed the same classifier; the turn-provenance state (which turns were wake-injected vs user-prompted - the settings-hook regime gets this from synthetic parts, which mods do not produce) lives in the BUNDLED SERVER keyed by the session id the mod passes per `$.mcp.call`, NOT in mod module state (reload wipes it - the same durability rule as the extraction buffer); `$.ui.notify` delivers with its documented resolution contract.
9. **Prediction/behavior engines** - host-agnostic already; only delivery rides the quirk list. Disposition: consume the stage tool like everything else.
10. **MCP server + sideband + version skew** - FOR on CC today: bridge "no in-process runtime". Quirk accommodation: the sideband UDS, the version file + skew detection (issue #6), auto-refresh-as-pseudo-plugin-load, silent-stdout discipline, deepPassthrough validation. **Disposition:** on the plugin regime the bundled server is called in-process and updates with the plugin - the UDS, version file, and auto-refresh die on THAT path; all of them survive for the settings-hook regime and Cursor (which keeps the sideband: its `flush-tools --json` rides the same UDS).
11. **System prompt delivery** - three independent string constants today (documented drift hazard, docs/dev/features/multi-host.md:149-158). **Disposition:** one template rendered in-process via `prompt.section`/`prompt.context` hooks; the CLAUDE.md marker machinery becomes settings-hook-regime-only, and its identity-teaching text (the `as`-spelling, src/prompts.ts:574) must be regime-conditional so the plugin regime never teaches the fallback's identity stack.
12. **Session tabs, redo** - near-100% opencode accommodation (rpc bridge, keymap layers); disposition: documented degradation, not a port.
13. **Session archaeology** (the opencode.db readers: `get_session_info`, `session_search`, `session_get`) - FOR: let the model learn session identity and conversation history. Quirk accommodation: entirely opencode-shaped (reads opencode.db; MCP hosts have no session database). **Disposition:** stays opencode-fenced on CC; the CC-native backend would be `transcript_path` JSONL plus `$.session.messages()` - recorded here as a FUTURE capability, deliberately not in this plan's scope (wrong-corpus risk if un-fenced without a new backend).

## Mandate 3: code structure for the dual-plugin setup

### Is HostCapabilities host-neutral? No - and the contract is re-derived, not stretched

**The single most load-bearing number for the structure question: a CC mod can faithfully implement 3.5 of HostCapabilities' 14 members (12 methods + 2 flags) - and two of those mappings are degenerate.** That ratio IS the quantification of Jeff's quirk-tailoring hypothesis: the shared runtime's lifecycle contract is almost entirely opencode-session-shaped, and no amount of adapter code can stretch it over a host with no session-creation API. HostCapabilities (src/capabilities.ts:29-143, introduced `b57fdc7` for v1/v2 compatibility: "whatever opencode version hosts it") maps as follows: `showToast` -> `$.ui.toast` (faithful); `compactSession` -> `$.session.compact` (faithful); `nativeCommands` -> true (CC mods register commands programmatically - the flag maps, though the arming contract differs from v2's CommandEditor); `sessionMessages` -> `$.session.messages()` (partial - lacks `info.error` and the synthetic flag the alert classifier needs); `promptSession` -> `$.prompt.submit` (degenerate only: idle-gated, self-session, always a real turn - no noReply, no child targeting); `noReplyDelivery` as a constant false. The other 8 members (`sessionCreate`/`sessionDelete`/`sessionGet`/`sessionList`/`sessionMove`/`enumerateSessions`/`fetchStatuses`/`exitHost`) have no CC surface, by design. **The seam is therefore re-derived from the concept map** into six host-neutral operations, and the mapping table below is the adapter contract both adapters must satisfy:

| Neutral seam operation | opencode adapter (maps onto HostCapabilities) | Claude Code mod adapter |
| --- | --- | --- |
| deliver-context (inject context into the session without a turn) | v1 `promptSession` noReply / v2 pendingInjections | `prompt.submit` -> `e.context` (next turn) |
| start-turn (proactively start a turn) | v1 `promptSession` async / v2 session.prompt | `$.prompt.submit` |
| notify-user (out-of-band signal) | TUI toast | `$.ui.notify` (with resolution contract) |
| run-child (dispatch a subordinate) | v1/v2 sessionCreate + promptSession | `$.agent.spawn` / named background subagent |
| compact | v1 TUI command / v2 session.compact | `$.session.compact` |
| exit | v1 app.exit / v2 tab-close event | degrades: `$.ui.notify` "safe to close" |

The runtime keeps its SDK-free import graph (src/index.ts:8-15, enforced by the subprocess-probe test in tests/opencode-v2-adapter-caps.test.ts:133-162); the CC adapter joins the same discipline with the same probe pattern (assert the mod graph never imports `node:*`).

### Target structure: a Claude Code plugin over the shared core

- `plugin/` (new): `.claude-plugin/plugin.json`, `hooks/register.js` (the mod), the bundled MCP server entry, skills, subagent definitions. Distribution: a thatch-owned marketplace repo; `/plugin install thatch@<marketplace>`. (The update-story addendum at the end of this doc REFINES this: the recommended route is an npm-sourced plugin entry inside a minimal marketplace - same install UX, no second release train.)
- **The mod is the lifecycle-and-delivery layer** (thin, capability-mediated only): `prompt.submit` (stage tool via `$.mcp.call`, inject `e.context`), `tool.call` (buffering via the server, greenlight tools), `turn.complete` (alerts verdict, wrap-up resolution, extraction trigger), `session.start` (registrations, reminders), `session.end` (cleanup, watcher death), `session.receive` (chat delivery), `classic.SessionStart` (reminder incl. `source: "compact"`), `$.clock.every` (watcher cadence), `$.prompt.submit` (chat wake, watcher delivery). **Every `tool.call` and `turn.complete` handler branches on `e.agentId`** - both events fire for SUBAGENT turns and calls too (events.md states it twice: tool.call fires "including calls a subagent makes", and a subagent's turn fires turn.complete with `e.agentId` set; the docs' own notify example filters on it for main-conversation-only), and without that branch every background subagent completion would fire a duplicate extraction run and spurious alert verdicts; the buffer keys by agent where subagent work is kept separate.
- **The bundled MCP server is the state-and-model layer**: unchanged shared tool core executes (src/tool-defs.ts), the DB, the warm embedding model, the stage computation. Full Node. Per-session (stdio), same as today's CC shape.
- **Regime coexistence (the two-regime problem):** the plugin regime is opt-in per setup, and opting in MUST deactivate the fallback's writers: remove the settings-hook entries (`replaceThatchHooks` only ever adds - src/setup.ts:285-295), remove the CLAUDE.md marker block, and give the bundled server a distinct entry point that skips sideband binding, version-file writes, auto-refresh, and behavior seeding (all four would otherwise fight the fallback regime and Cursor's server - the socket path and version file are hashes of the shared dbPath, src/sideband.ts:15, src/version-check.ts:64). A regime marker the server reads decides which mode `checkSetup` reports. Without this, auto-refresh (src/mcp.ts:244-259) silently resurrects the fallback hooks on every session start and both regimes deliver every prompt. **The disabled-mod hole:** `disableAllHooks` and enterprise `allowManagedModsOnly` stop the mod's hooks but LEAVE the plugin's server, skills, and commands loaded - a user in that state would have deleted fallback hooks and a dead delivery layer (silent feature loss). So opt-in also writes a marker the bundled server can detect, and the server warns on its first `tools/call` response (and `checkSetup` reports it) when the mod's liveness ping has gone silent - mirroring the existing setup-warning channel, src/mcp.ts:216-221. (`--safe-mode` is different: it disables the ENTIRE plugin including the bundled server - user-invoked, visible, and `checkSetup` is the only reporter; no warning channel exists when the server itself is dark.) Downgrade detection is reader-specific: an uninstalled plugin leaves nothing behind to warn, so detection belongs to the FALLBACK regime - `checkSetup` (or the next setup run) detects the orphaned marker and offers to reinstall the fallback hooks.
- **What happens to today's integration:** src/mcp.ts survives as the bundled server (plugin regime) + the standalone server (Cursor and pre-mod CC); setup.ts shrinks to plugin install + fallback-hook writing for pre-2.1.287 CC; bin/thatch's hook subcommands (`buffer-batch`, `buffer-tool`, `flush-tools`, `flush-predictions`, `reminder`, `chat-notify`) become the documented fallback regime (the `session`/`chat` CLI subcommands are regime-independent and unchanged); extract-queue stays for Cursor and the fallback.
- **Testing shape (stated honestly):** the mod's decision logic is pure against a mocked `$` (hand-rolled double in tests/mocks/) and reaches CI under bun test; the integration layer (real CC loading the plugin) has no sandbox or CI leg today and stays manual/live QA unless the QA matrix gains a CC leg. The v1 caps mapping (capabilitiesFromClient) has no direct unit test - the re-derivation gains a mods-`$` mock harness AND v1 caps tests as an explicit dependency before any behavior migrates.

## Alternatives weighed (round-1 lens verdicts)

- **No plugin - harden the settings-hook regime to parity:** honest as an indefinite fallback and lower team cost, but it permanently rations watchers and native wake (no `$.prompt.submit`/`$.clock.every`) - exactly the silently-missing-features pain the mandate says to judge against - while the nudge delivery layer's five-field guessing and text-equality bindings live on. Rejected as the end state; kept as the fallback.
- **Mod + separate long-lived daemon** (shared warm model across sessions, like `opencode serve`): rejected. The delivery problem survives the daemon unchanged (no channel into an idle CC session - the conclusion thatch already recorded when rejecting a daemon for the MCP chat path, docs/dev/features/cross-session-chat.md:572-576), and it reintroduces the v2 reload/orphan/rehydration failure class the project spent years escaping. The memory concern it would solve is better addressed by shrinking the bundled model if quantification (below) demands it.

## Addendum: the update story (npm-as-plugin-source, verified 2026-11-05)

Jeff's question: does distribution move to npm, what does Claude Code's own update UX give us, and what survives of the npm-update nudges. Commissioned as a design addendum only; nothing here is implemented. All claims verified against the live plugin docs (plugins/install.md, plugins/publish.md, plugins/marketplace-reference.md, fetched 2026-11-05).

### What the docs actually say (the verified facts)

- **npm IS a valid PLUGIN source - the prior "marketplaces are git-only" belief is half-right.** A plugin entry may fetch `{ "source": "npm", "package": "@org/pkg", "version": "^2.0.0" | dist-tag | omitted(= latest), "registry": "https://..." }`. But `npm` as a MARKETPLACE source fails to load ("NPM marketplace sources not yet implemented") - so the shape is always: a git-or-hosted marketplace.json whose PLUGIN ENTRY points at npm. An npm-sourced plugin's install scripts never run, and its dependencies install separately from a supported lockfile, also script-free.
- **Version semantics**: `plugin.json`'s `version` decides updates - `claude plugin update` reports "already at the latest version" when the string is unchanged. In a git-hosted marketplace you may OMIT `version` and Claude Code versions by commit SHA (every push is a release). The npm source's own `version` field can be a range, a dist-tag, or latest.
- **Update UX (the user's side)**: `claude plugin update <name>@<marketplace>`; per-plugin "Update now" in the `/plugin` panel; "Update marketplace" for the listing. There is NO update-all command. **Auto-update is a per-marketplace USER setting, OFF by default for every third-party marketplace** (on by default only for Anthropic's official names and claude.ai-synced ones). When enabled, it refreshes marketplaces after session start and updates on-disk copies; the RUNNING session keeps its loaded versions and shows `Plugin updated: <name> · Run /reload-plugins to apply` - applying warns when it would invalidate the prompt cache (`/reload-plugins --force` costs one uncached request).
- **CLI-shipped plugins (the documented pattern)**: "publish the plugin in a marketplace and have your installer or post-install message run or print the two commands" - `claude plugin marketplace add <source>`, then `claude plugin install <name>@<marketplace>`. A CLI can also emit the `claude-code-hint` tag (plugins/cli-hints.md) so a Claude Code session suggests the official-marketplace install in-session.
- **Install scopes**: user (all projects), project (committed `.claude/settings.json` - collaborators still run one install), local. `--plugin-dir` stays the load-for-one-session path (the QA path this branch already uses).
- **Renames**: never rename a published plugin; the marketplace's `renames` map migrates installs.

### The decision: npm-sourced plugin entry inside a minimal marketplace (recommended)

Three options weighed:

1. **Git marketplace repo, plugin by relative path (the plan's current letter).** The marketplace.json lives in a thatch-owned repo listing the plugin at `./`. Release = bump `plugin.json`'s version (or omit it and let every push be a SHA release). Cost: a SECOND release train - npm releases (the standalone regime's channel) and marketplace-repo state must stay in lockstep, or plugin users and npm users see different versions of "latest". The thing the project already got wrong once with the version-skew file, repriced as a process burden.
2. **npm-sourced entry (recommended).** The marketplace.json (which can live in the thatch repo itself) lists the plugin with `{ "source": "npm", "package": "<the existing npm package>" }`. **The npm release IS the plugin release** - one version, one changelog, one existing release process; no lockstep. Version pinning comes free (`version: "^0.3"` per user; `latest` default). Constraints: no install scripts run (thatch has none - `bin/thatch` runs under bun directly); **the plugin root must ship a supported LOCKFILE for its dependencies to install at all** (the docs' separate dependency-install step runs only off a lockfile beside package.json - npm-shrinkwrap.json is the recommended form; the repo's bun.lock exists but is NOT in package.json's `files`, so today's published package would land a bundled server with NO node_modules and unresolvable deps - a packaging change is a PRECONDITION of this option, not a nicety); the manifest's server command must not assume `thatch` is on PATH - it resolves as `${CLAUDE_PLUGIN_ROOT}/bin/thatch` (the documented path-substitution form) invoked with bun (already a stated prerequisite).
3. **Anthropic's directory.** Reaches claude.ai/Cowork surfaces and syncs with auto-update ON - but requires a paid claude.ai plan to submit and Anthropic's review; a later, optional step AFTER the npm route works, not the distribution spine.

Setup's claude-specific branch under this decision: `thatch setup --claude --plugin-regime` keeps generating the local plugin dir for QA (`--plugin-dir`), and gains the marketplace handoff as its production path - print (and offer to run) the two documented commands instead of only the load instruction. The generated-dir path remains for dev/QA/offline installs; the regime marker and deactivation logic are identical under both (the plugin content is the same shape either way).

### The update nudges, mapped per regime

- **The settings-hook regime (unchanged)**: the npm update checker (`startVersionChecker`), the flush-tools update warning, and the version-file skew gate all stay - they are standalone-mode machinery and the fallback regime keeps the standalone server.
- **Plugin regime (this plan's Step A skips all three)**: skew detection stays dead - it exists to catch hooks and server disagreeing, and the plugin updates them together. **The update-AVAILABLE warning, however, should be revived in bundled mode** (design note for Step A's follow-up): the bundled server has full Node and can run the same npm-latest cache check, warning on the same first-tools/call channel it already uses for the disabled-mod warning - no version file needed (nothing reads one on this path; the warning is direct). This closes the real regression Step A introduced: with auto-update off (the default for our marketplace), a plugin user otherwise never learns a new thatch exists.
- **The host's own update signal** (`Plugin updated · Run /reload-plugins`) is the delivery of the update itself; our module-state-wipe-on-reload design (server owns all durable state) and session-static instructions (the prompt-cache warning costs one uncached turn at most) are already aligned with it.

### Acceptance criteria for this addendum (when implemented)

- The published npm package ships a supported lockfile (npm-shrinkwrap.json preferred) - WITHOUT it the npm-sourced install lands no node_modules and the acceptance criteria below are unmeetable (the evidence audit's finding).
- The marketplace.json ships in the thatch repo with the npm-sourced entry; `claude plugin validate` passes; install from it lands a working bundled server (resolved via `${CLAUDE_PLUGIN_ROOT}`, bun on PATH).
- `thatch setup --claude --plugin-regime` offers the marketplace handoff (print + opt-in run of the two commands); the generated-dir QA path survives.
- Bundled mode warns update-available on first tools/call (no version file, no skew); auto-update-off users get the same notice the hooks regime gives.
- Renames: the plugin name is permanent from first publish; any later rename goes through the marketplace `renames` map.
