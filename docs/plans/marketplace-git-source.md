# Marketplace: switch the thatch plugin entry from npm source to a git source

**Status: CONVERGED (round 2: reviewer CONSENSUS 0 blockers; evidence and consistency audits both PASS on this text; the round-2 reviewer's two prescribed one-line corrections - job-level contents:write, stale-branch wording - are applied).** Jeff's ruling 2026-11-20, defect 1 of the claude distribution review, option (b): the marketplace entry moves from the npm package to a release branch of this repo carrying the prepack-generated plugin tree, so installs never run npm's tarball-URL pack and never need `npm_config_allow_remote`.

## Synopsis

Today `.claude-plugin/marketplace.json` sources the plugin from the published npm package (`{source:"npm", package:"@jeffober/thatch"}`). On npm 12 that install fails with `code EALLOWREMOTE` (docs/user/setup.md:88-111, anthropics/claude-code#98362): Claude Code's installer runs `npm pack` on the resolved tarball URL (2.1.330 binary string: `"npm pack failed"`), and npm 12 refuses remote-URL pack arguments. The fix routes the install around npm entirely: a `plugin-release` branch of this repo, regenerated by CI at every tag, carries the plugin tree (generated manifest, hooks, slim lockfile); the marketplace entry points at it with a `github` source pinned to the branch. Installs become a git clone plus a bun dependency install. The npm package keeps its other consumers; it stops being the plugin install path.

## Researched facts (evidence, not memory)

All binary citations are strings extracted from the installed claude 2.1.330 binary (`~/.local/share/claude/versions/2.1.330`); docs citations are docs.claude.com/plugin-marketplaces (fetched 2026-11-23).

### (a) Marketplace-entry git source shapes

The plugin-entry source union schema in the binary accepts: `npm`, `url`, `github`, `git-subdir`, `archive`, `command` (type-name set `["npm","url","github","git-subdir","archive","command","unsupported"]`). The git-family members relevant here:

- `github`: `{source:"github", repo:"owner/repo", ref?: "Git branch or tag to use (e.g., \"main\", \"v1.0.0\"). Defaults to repository default branch.", sha?: "Specific commit SHA to use"}`.
- `url`: `{source:"url", url:"Full git repository URL (https:// or git@)", ref?, sha?}` - the git-by-URL shape for plugin entries. (`git` exists only as a MARKETPLACE-source type, not a plugin-entry type; plugin entries have no `git` member.)
- `git-subdir`: `{source:"git-subdir", url, path (min 1), ref?, sha?}` - sparse checkout (`--filter=tree:0`) for a plugin inside a monorepo subdirectory.

Official docs match: the source table lists `github` = `{ "source": "github", "repo": "your-org/my-first-plugin" }` and `git-subdir`, with `ref`/`sha` pinning documented in the marketplace reference.

**Chosen shape:** `{source:"github", repo:"sysread/thatch", ref:"plugin-release"}` - the plugin tree is the repo ROOT of a dedicated branch, so `git-subdir`'s `path` is unneeded and `url`'s full-URL form buys nothing over the owner/repo shorthand.

### (b) What a git-source install does

Install clones the source at the pinned ref and reads `.claude-plugin/plugin.json` from the clone (docs: "Claude Code first fetches a `github`, `git-subdir`, or other remote source when you install the plugin"; the entry name must match the manifest name). The tree lands in the plugin cache (`~/.claude/plugins/...`).

The dependency install runs on the cached tree and picks the package manager BY LOCKFILE PRESENCE (2.1.330 binary, the `Opt` table, in priority order):

1. `bun.lock` present -> `bun install --frozen-lockfile --ignore-scripts` (the clone itself shells out to `git clone --depth 1 --branch <ref>`; the ref accepts a branch or tag)
2. `npm-shrinkwrap.json` or `package-lock.json` -> `npm ci --ignore-scripts --workspaces=false --no-audit --no-fund`
3. `bun.lockb` -> `bun install --frozen-lockfile --ignore-scripts` (binary lockfile cannot be pre-checked; the binary says "ship a text bun.lock instead")

So with the repo's text `bun.lock` beside `package.json`, the dependency install runs **bun** - npm is never invoked, and npm 12's allow-remote gate is unreachable. bun must be on PATH (the same prerequisite the server launch already has; docs/user/setup.md:94-98), and so must git (the install shells out to `git clone` - not a new requirement; `marketplace add` already clones).

The shipped lockfile must be the SLIM one (scripts/prepack.ts: the runtime closure only) - Claude Code installs every package the lockfile lists, so the full lockfile would land ~1 GB of devDependency trees in every plugin cache (tests/qa/live/claude/uc-146 header).

### (c) Update path and displayed version

`claude plugin update <name>` re-fetches the source "as the marketplace lists it" and records the commit then in use (2.1.330: "...fetching its source as the marketplace lists it instead. `claude plugin update` records the commit then in use"). With `ref` naming a BRANCH, updates follow the branch head. A full-commit-id ref is held - "refreshes and auto-updates do not move it" - but that describe lives on the marketplace-SOURCE ref schema, so applying it to plugin-entry refs is an inference from a real string, not a directly stated rule. We pin the branch: `plugin update thatch` (or "Update now" in /plugin) picks up the regenerated tree.

Displayed version resolution order for git-family sources (2.1.330, the `mye` function): the plugin manifest's `version` first ("Using manifest version for ..."), then the entry/catalog version, then the git sha (first 12 chars). Our generated `.claude-plugin/plugin.json` carries `version: pkg.version` (src/setup.ts:636), so the displayed version is the release version - the npm package remains the version source of truth.

### (d) CI shape

`bin/release` bumps the version, tags `v<next>`, pushes; the tag triggers `.github/workflows/publish.yml`, which runs the check matrix (bun 1.3.14 + 1.4.2) and then `npm publish --access public` (prepack generates the plugin tree into the tarball; postpack restores the working tree).

The new step rides the SAME workflow: a `plugin-branch` job that checks out the tag, runs prepack's generator, commits the generated tree to `plugin-release`, and force-pushes. The generated tree is exactly what prepack produces (scripts/prepack.ts): `.claude-plugin/plugin.json` (manifest with the bundled-server command), `hooks/` (hooks.json, register.js, instructions.js, mod.js), slimmed `package.json` + `bun.lock`. No npm publish is needed for the branch to serve installs.

### (e) The mcpServers manifest command under a git source

`${CLAUDE_PLUGIN_ROOT}` substitution is source-agnostic. The binary: "Path placeholders like ${CLAUDE_PLUGIN_ROOT} are substituted per-element as plain strings" for stdio server commands, and the substitution replaces the placeholder with the plugin's installed path. The generated manifest's command (`bun`, args `["${CLAUDE_PLUGIN_ROOT}/bin/thatch", "mcp", "--bundled"]`) works unchanged: the literal is passed by scripts/prepack.ts:31-34 into the manifest spread at src/setup.ts:640-642, and `bin/thatch` imports `../src` (bin/thatch:12-18), so the branch tree must carry `src/` - the full tag checkout does.

### (f) Marketplace definition and plugin tree on different refs of one repo

The marketplace definition lives on main (`.claude-plugin/marketplace.json`, committed; scripts/postpack.ts: "the repo IS the marketplace"). `marketplace add sysread/thatch` fetches only the marketplace definition; the plugin entry's `github` source is fetched separately at its own ref at install time. Nothing in the binary couples the two fetches - the marketplace clone lands under `~/.claude/plugins/marketplaces/`, the plugin tree under the plugin cache, each from its own clone. The docs describe exactly this decoupling (a marketplace entry can point at any repo). Tolerated by construction.

### Composition: the marketplace-components worker

Another delegate (marketplace-components) is adding component arrays to the same entry concurrently. Interaction to respect, from the binary: an entry that declares components (`commands`/`agents`/`skills`/`hooks`/`outputStyles`/`themes`) while the plugin's own `plugin.json` also declares them is a CONFLICT that fails the install unless the entry sets `strict: true` ("Plugin ... has conflicting manifests: both plugin.json and marketplace entry specify components. Set strict: true in marketplace entry ..."). That rule is unchanged by the source-type switch: this plan touches ONLY the `source` field and composes with whatever component fields their change lands. Whoever lands second resolves the strict flag question.

## Design

1. **Branch:** `plugin-release`, written ONLY by CI (force-push, one writer) after a one-time hand-seeded landing commit. One commit per release: the tag's tree plus the prepack-generated paths (`.claude-plugin/plugin.json`, `hooks/`, `package.json`, `bun.lock`). The branch also carries `.claude-plugin/marketplace.json` (it is the tag's tree) - inert for installs: the installer reads the clone's `plugin.json`, not the marketplace file.
2. **CI (publish.yml):** add a `plugin-branch` job (needs: test) that: checks out the tag; `bun install`; `bun scripts/prepack.ts`; configures the git identity; commits the four generated/changed paths with message `plugin tree for v<version>`; `git push --force origin HEAD:refs/heads/plugin-release`. The job needs a job-level `permissions: contents: write` - the workflow pins `permissions: contents: read` at the top (publish.yml:10-12), and GITHUB_TOKEN capped at read cannot force-push regardless of repo settings. The job also gets the failure-report step the publish job has, so a blocked first push is visible. It runs alongside (not inside) the npm publish job, so a publish failure does not block the branch refresh and vice versa. Precondition to verify at implementation: repo settings let the workflow's token force-push `plugin-release` (no branch protection or ruleset blocking it on top of the token permission).
3. **Marketplace entry (main):**
   ```json
   "source": { "source": "github", "repo": "sysread/thatch", "ref": "plugin-release" }
   ```
4. **npm package role afterward:** unchanged. It stays the release train (version source, bin/release flow) and serves its other consumers (opencode plugin installs, `bunx`/npm CLI use). The npm tarball keeps shipping the plugin tree (prepack still runs on publish) - it is just no longer the marketplace's fetch route.
5. **Docs story:** setup.md's Claude Code section loses the npm-12 EALLOWREMOTE workaround block (the gate becomes unreachable) and keeps the prerequisites, reworded: git and bun on PATH - bun runs the server AND the dependency install (`bun install --frozen-lockfile --ignore-scripts` on the shipped slim lockfile), git runs the clone. The install is a git clone of `plugin-release` at the tag; `claude plugin update thatch` re-clones the branch head.

## State and transition

Install, before (npm source): `npm pack <tarball-url>` (npm 12 gate) -> unpack -> bun dep install on slim bun.lock -> cache.

Install, after (git source): `git clone sysread/thatch` at `plugin-release` -> read `.claude-plugin/plugin.json` -> copy tree to plugin cache -> bun dep install on the committed slim bun.lock -> cache. No npm invocation anywhere in the path; no `npm_config_allow_remote`.

Update, before: re-pack the npm tarball (same gate on npm 12; docs told users to re-prefix the env var). Update, after: re-fetch `plugin-release` HEAD, record the new commit sha, re-run the bun dep install.

Existing npm-sourced installs, after the flip: the marketplace's listed source type changes under a cache entry that records no git sha. Whether `claude plugin update` reconciles an npm->github switch in place (re-clone vs reuse vs error) is NOT verifiable from the binary; it is a live check, not a premise. The test plan carries it; if it errors, setup.md gains a one-time "reinstall" note for existing installs.

Version, before and after: the plugin.json manifest version (= the npm package version at the tag). Unchanged surface.

## Risks

- **Landing window:** between the release commit reaching main and the workflow pushing `plugin-release`, a fresh install clones a STALE branch (the previous release's tree) for the workflow run's few minutes; it is minutes old, not broken - the next update catches up. The MISSING-branch case exists only before the first hand-seed. FIRST release carrying the flip: the entry lands TOGETHER with a hand-seeded `plugin-release` (checkout of the current release tag, prepack applied, branch pushed) - then the steady state above holds from the start.
- **Full-tree clone:** the git source caches the whole tag tree (src, tests, docs, assets) rather than an npm tarball's `files` subset. The clone is shallow (depth 1 at the ref), so size is one commit's tree; repo is small; accepted. `git-subdir` does not help (the plugin lives at the root).
- **Force-push branch:** a user-side `git` never touches it; CI is the sole writer, so force-push cannot lose human work. The token-permission precondition is checked at implementation (Design item 2).
- **strict-flag interaction** with the components change - tracked in the composition section above; not this plan's decision.
- **Existing npm installs** - the migration live check (State and transition, Test plan); worst case is a documented one-time reinstall.
