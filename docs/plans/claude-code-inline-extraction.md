# Claude Code: inline extraction (retire the sub-agent handshake)

**Status: CONVERGED (round 5 + coordinator review + final evidence/consistency audits, both PASS).** Mitigation for the issue #22 nudge loop landed on main as `6ea9967` (buffer meta-tool exclusions). This plan migrates the Claude Code extraction flow off the model-driven sub-agent handshake onto the inline path. **Implementation is HELD** pending Jeff's review; this doc is the only artifact of the planning work.

## Goal

On Claude Code, extraction should complete with zero sub-agent dispatches: the parent receives the queued payload directly at prompt time, processes it inline, and acks. The `SubagentHandback`/`ToolSearch` exhaust class dies by construction instead of by deny list. Cursor's flow is unchanged.

## Background

The Claude Code extraction flow today (citations verified against main `6ea9967`):

1. `PostToolBatch` hook runs `thatch buffer-batch`, which funnels into `appendBatch` (src/extract-queue.ts:61) - a file-backed JSONL queue per session, peek-not-drain (src/extract-queue.ts:126).
2. `UserPromptSubmit` hook runs `thatch flush-tools` (bin/thatch:1387). Flush stage 1 peeks the queue and emits `extractionNudge` (bin/thatch:1480-1486), which instructs the model to **spawn a background sub-agent** and ack with `mcp__thatch__extraction_done` (src/prompts.ts:962-1007).
3. The extractor sub-agent calls `mcp__thatch__get_extraction_payload` with the parent's session id (src/tool-defs.ts:798), runs the fact-extractor skill, and acks; `extraction_done` with the parent's session id drains the queue (src/mcp.ts:177-181, src/tool-defs.ts:880-887). The parent's own `memory_remember` save also drains (src/extract-queue.ts:69-86).
4. The sub-agent's return call (`SubagentHandback`) and the parent's `ToolSearch` schema loads land in the **parent's** queue under the parent's session id - every completed extraction queued the next nudge (GitHub issue #22; mitigated by `6ea9967`, which excludes all six meta-tool spellings in `appendBatch`).

### History of the dispatch (why it exists and why we are retiring it)

Inline delivery is the **restoration of the original design**, not a novelty:

- `39831b2` (2026-07-07, "Close Claude Code extraction parity gap with file-backed queue") inlined the full payload in the nudge and the parent processed it inline.
- `ff8e2f6` (2026-07-17) suggested a sub-agent but kept the payload inline, with inline as the explicit fallback.
- `0dafeeb` (2026-08-14, "Fetch extraction payload by session ID instead of inlining in nudge") made dispatch mandatory. Its body gives exactly one reason: keep the payload out of the main session's context window ("tens of KB"). No delivery failure was recorded on either side of that trade, and no inline fallback survived it.

This plan trades that context saving back: the dispatch is the only step that manufactures loop exhaust (issue #22), and filtering it - the landed `6ea9967` deny set - is maintenance without an end, because dispatch-tool names are host- and version-dependent. Opencode already deleted its model-driven handshake for the same class of reason (docs/dev/features/extraction.md "Key invariants" #2). **Note on direction drift:** the issue #22 fix comment named a `mcp_tool`-hook-based inline path as the structural direction; this plan instead delivers the payload through the existing command hook and demotes the `mcp_tool` variant to a held alternative - the reasoning is in the alternatives subsection below.

### Verified Claude Code facts this plan relies on

- Hook stdout and `additionalContext` are capped at **10,000 characters**; over the cap the text is saved to a file in the session directory and replaced with the file path plus a 2,000-character preview, and "Claude Code doesn't ask Claude to read the file" (hooks reference, "JSON output" section). No setting raises the cap.
- `UserPromptSubmit` supports all five handler types; `mcp_tool` and `command` hooks default to a 30-second timeout there, and a timed-out hook's output is discarded while the prompt proceeds (fail-open).
- `mcp_tool` hooks landed in Claude Code **v2.1.118** (CHANGELOG.md, "Hooks can now invoke MCP tools directly via `type: "mcp_tool"`"). They bypass deferred tool loading. `SessionStart` `mcp_tool` hooks do not run at launch (no MCP client context); `UserPromptSubmit` has no such problem. (Version claim is load-bearing only for the held step 4 - re-verify against the changelog on revival, so changelog drift cannot fail an audit of an unimplemented step.)
- `PostToolBatch`'s per-call schema carries no agent attribution (`tool_name`/`tool_input`/`tool_use_id`/`tool_response` only); `agent_id`/`agent_type` are top-level fields of the whole hook invocation. Per-call sub-agent filtering is therefore not available to the buffer.
- Agent hooks (`type: "agent"`) are experimental and get Read/Grep/Glob; the hooks reference does not state the MCP prohibition explicitly - inferred from the tool list, and non-load-bearing (they cannot be the extractor either way).
- `mcp_tool` hooks bypass deferred tool loading - mechanism-inferred from the reference (hooks call the server directly), stated verbatim nowhere; non-load-bearing (supports an alternative the plan rejects).
- `UserPromptSubmit` also fires when a background subagent reports back and on cross-session messages - the same events `flush-tools` already sees.

## Proposed approach

**Inline payload delivery through the existing `flush-tools` command hook.** When flush stage 1 finds a non-empty queue on Claude Code, `flush-tools` prints the inline-processing instructions followed by the extraction payload itself - the same JSON `buildExtractionPayload` produces today - instead of the sub-agent dispatch nudge. The parent model processes the payload in context, writes memories with `mcp__thatch__memory_remember`, and acks with `mcp__thatch__extraction_done` (passing its own session id, the same shape `extractionDirectPrompt` already teaches, src/prompts.ts:1016-1023). No sub-agent, no handback, no fetch tool call.

The payload is a truncated digest of the session's tool calls, so inline delivery adds no new injection surface - the dispatched extractor saw the same payload in the dispatch world. Note the digest is not strictly limited to what the parent saw: other sub-agents' tool calls can land in the parent's queue under the parent's session id (GitHub issue #22's NOTES section), so the payload may include interactions the parent never observed - the same exposure the dispatched extractor already had. It re-enters context at ~500 chars per interaction (args capped at 120 by `summarizeArgs`, src/extraction.ts:14) instead of full tool results. The context cost the dispatch nudge avoided is accepted back: worst case 20 interactions (`MAX_BUFFER`, src/extract-queue.ts:14), typically a few KB.

**The payload, or its queue-file path over the cap, is delivered at every escalation level.** The escalation ladder changes tone only - polite, insistent, shouting - and never withholds delivery. A pointer-only variant was evaluated and rejected: with the fetch tool retired on this host and the queue path unknown to the model, a pointer without a Read instruction either stalls the queue forever or invites an unprocessed ack, which on this path is a hard drain (silent interaction loss, the accept-before-fetch class the code warns about at src/extract-queue.ts:88-98). Delivery plus escalation is also the shape the original inline design used (`39831b2`).

**Re-feeding by the parent's own processing is bounded, not denied - and order-sensitive.** While processing, the parent may make ordinary tool calls (Read/Grep to verify a candidate fact); those buffer as normal interactions. The first saving `memory_remember` drains the ENTIRE queue file (src/extract-queue.ts:82-86), so a verify-then-save order silently drops the verifying interactions: only interactions buffered after the save re-feed. The nudge therefore instructs **save first, then verify** ("save durable facts as you identify them; further tool work after saving will be picked up by the next nudge"). The re-feed tail is correct behavior - the new interactions are real work deserving extraction - and is bounded by the 20-cap and the escalation ladder. The QA cycle test covers both orders.

### The 10,000-character cap is handled by the hook, not gambled on the host fallback

`flush-tools` measures what it is about to print. If instructions + payload exceed a conservative threshold (~9,500 chars), it prints the instructions plus the queue file's absolute path ("the payload is at <path>; Read it, process it, then ack") instead of the body. This is deterministic, works on every Claude Code version, and does not depend on the host's own over-cap fallback (which saves to a session file the model is never asked to read). The host fallback remains a second safety net behind it. Static instructions also carry unconditional wording: "if the payload below appears as a saved-output file path instead of JSON, Read that file first."

### Alternatives weighed (round-1 lens verdicts)

- **`mcp_tool` hook delivering the payload (the issue-comment direction):** set aside. It buys no delivery determinism over `flush-tools` stdout - both are host-owned, and both still depend on the model choosing to process delivered text. It costs a version gate (>= 2.1.118 plus a fallback matrix in setup), a second hook invocation per prompt, a purpose-built server-side wrapper tool (a bare `get_extraction_payload` call would inject "No queued tool interactions found" into context on every prompt), and a suppression protocol so stage 1 and the new hook do not double-deliver. The 10,000-character stdout cap applies to both designs equally.
- **Stop-hook end-of-turn extraction:** rejected. The only model-visible `Stop` channel is exit-2 block (a forced continuation turn charged to the user), it collides with the "stop, do not advance pending work on this nudge's account" discipline, and the missed-nudge counter lives at the prompt boundary a Stop flow never passes through - a harder-to-escalate cousin of issue #22.
- **Headless extractor (hook or warm server extracts without the host model):** the only design that removes model compliance from the loop by construction, but it needs a new sideband method (the sideband is embed-only, src/sideband.ts:123-129), an LLM client with credentials in the CLI, and a second implementation of the fact-extractor skill. The squeeze vastly exceeds the juice over a prompt-text change. **It is the named revival candidate** if "model ignores payload" ever shows up at scale - strictly stronger than the held `mcp_tool` variant, which still depends on model processing.

### The flush-stage extraction is a prerequisite inside the core step

The stage logic lives in bin/thatch - outside tsconfig (tsconfig.json `include: ["src"]`), untestable from bun test - and the acceptance criteria below demand unit tests for the host branch, the cap behavior, and the escalation levels. Those tests are **unwritable while the logic stays in bin/thatch**. So the core step first extracts the `flush-tools` stage logic into `src/flush.ts` as a pure function (parsed hook payload + db path in; ordered emit lines out), with bin/thatch as a thin dispatcher (see "Code organization" for the layout decision). QA use cases uc-009/uc-017/uc-044 already run the real CLI and remain the end-to-end net.

## Queue state and transition matrix (per session, Claude Code)

| State | Meaning | Transitions out |
| --- | --- | --- |
| EMPTY | no queue file | buffer real interaction -> PENDING |
| PENDING | queue file non-empty, missed count k>=0 | buffer -> PENDING (20-cap trims oldest); flush stage 1 -> ESCALATED(k+1) with payload delivered; skew gate -> SKEWED pause notice, count unchanged; `memory_remember` save (appendBatch gate) -> EMPTY, count cleared; `extraction_done` with session id -> EMPTY, count cleared |
| ESCALATED(k) | PENDING plus k consecutive nudges delivered without a save or ack; tracked by the missed-nudge counter | same drains as PENDING; tone changes at k>=2 (insistent) and k>=3 (shouting); payload, or its queue-file path over the cap, always delivered |
| SKEWED | PENDING and version skew detected | exits when skew clears (session restart); queue untouched, file-backed |

Precedence in `flush-tools`, unchanged: skew gate > extraction stage > recall/prediction > write nudge. The extraction stage consumes a flush even when the model ignores it - exactly today's behavior. `get_extraction_payload` never appears in the Claude Code transitions; peek-not-drain survives unchanged, so a crash or interruption loses nothing (the queue is file-backed). The SKEWED pause keeps its original rationale on Claude Code: the inline nudge still names `mcp__thatch__extraction_done`, which the old-server tool set lacks (tests/version-skew.test.ts:60-79), so delivery pauses until the session restarts - unchanged from the dispatch world. One reachable model-error state, named for completeness: a malformed `extraction_done` without a session id resets the missed-nudge counter via appendBatch but drains nothing; the next flush re-delivers at polite tone. Harmless.

Escalation counter semantics note: on this path only a save or an ack resets the count (today the cheap dispatch ack resets it every cycle), and `UserPromptSubmit` also fires on background-task completions and cross-session messages - so escalation arrives faster than in the dispatch world. Accepted: the counter exists to bound ignoring, and faster escalation to a louder tone is the intended direction. The 20-cap bounds context cost.

## Code organization

Jeff asked this question by name, so the layout thinking is explicit. Today the Claude Code integration is smeared across four files: src/setup.ts (hook config writing, src/setup.ts:227-295 and `setupClaudeCode`), bin/thatch (the `buffer-batch` / `buffer-tool` / `flush-tools` / `chat-notify` / `reminder` subcommands), src/extract-queue.ts (the file-backed queue), and src/mcp.ts (the MCP server plus the extraction payload/drain providers). Three layouts were weighed:

1. **In-place edits only.** Minimal diff, but the flush-stage logic stays in bin/thatch - outside tsconfig (tsconfig.json `include: ["src"]`), untestable from bun test - and the acceptance criteria demand unit tests on exactly that logic. Rejected as the sole move.
2. **A full host-adapter taxonomy**: a `src/hosts/` (or `src/claude-code/`) module owning hook-config writing, the flush stages, queue adoption, and the host-keyed prompt sections, with Cursor joining if its shape fits. Rejected for this change, with reasons, not vibes: it is a package restructure riding a feature change, which the house dogma forbids in the same diff (restructuring changes import paths and review surface for everyone downstream); there is no third MCP host on the horizon to give the taxonomy a second tenant; and setup.ts already carries a serviceable `host: "claude" | "cursor"` concept, so the consolidation would mostly relocate code it does not simplify.
3. **The chosen middle path**: extract the flush-stage logic into `src/flush.ts` as a NEW module (parsed hook payload + db path in; ordered emit lines out) with bin/thatch as a thin dispatcher; add `adoptQueue` to src/extract-queue.ts (its only new export); keep host-keyed prompt content inside src/prompts.ts, whose `mcpInstructions` already takes a host parameter. Trade-off named: this buys unit testability for every stage on both hosts without moving any import path that exists today - `flush.ts` is an addition, not a restructure, so the dogma's release-safety concern does not apply. What it deliberately does NOT buy: a single-file home for "everything Claude Code" - hook config stays in setup.ts, subcommand plumbing stays in bin/thatch - because consolidating those is layout churn with no behavior or testability gain under the current two-host world.

**Trigger condition for revisiting:** when Cursor migrates to inline delivery, or a third MCP host arrives, the host-specific content (hook config writing, payload field names, prompt branching) will have outgrown the two-host shortcuts - at that point the host-adapter consolidation in option 2 earns itself and should be its own standalone draft PR.

## Migration steps (each independently shippable, release-safe)

1. **Part 1 - done, landed `6ea9967`.** The `appendBatch` meta-tool deny set covers all six spellings. This is the mitigation the migration stands on.
2. **Core: Claude Code inline extraction.** (a) Extract flush stages to `src/flush.ts` (bin/thatch becomes a thin dispatcher; no behavior change); (b) prompts.ts inline nudge with the shared escalation ladder; (c) flush stage-1 host branch prints instructions + payload, with the hook-side ~9,500-char cap and file-path fallback; (d) `mcpInstructions` host-keyed inline paragraph; (e) fact-extractor skill artifact inline branch + pinned contract update; (f) `get_extraction_payload` / `extraction_done` description updates and the comment-debt list; (g) docs both tiers (docs/dev/features/extraction.md, docs/dev/features/nudge-pipeline.md, docs/dev/mcp-parity.md, docs/user/extraction.md); (h) tests: unit (host branch, cap behavior, escalation levels, Cursor pin, skill artifact contract) + QA (per-host splits for uc-003-extraction-nudge, uc-009-flush-tools-tiers, uc-020-extraction-escalation, and uc-044-tier-priority - the latter two assert the real flush output contains `get_extraction_payload` and a session id, the dispatch shape, which fails on Claude Code under inline; a new QA use case asserting the Claude Code flow contains no dispatch instruction and completes a full inline cycle - buffer, deliver, process with a verifying tool call in both save-first and verify-first orders, save, ack - leaving the queue empty). Rollback: revert the commit - no config, no state migration; the queue file format is untouched. Any Claude Code version is supported (plain command-hook stdout, no version gate).
3. **Queue adoption across session forks.** Claude Code session ids change under the user (fork, resume, team features), stranding the old session's queue file. Step: when the current session's queue is empty AND no adoption has been attempted for this session id, resolve the predecessor session id from `transcript_path` and, if the predecessor's raw-id queue file exists, adopt it (rename to the current session id, missed count file moved with it). **Bounded trigger:** a one-attempt sentinel file per session id in the queue dir (`<safeName>.adopted`, written after the first attempt regardless of outcome) - the predecessor scan readdirs up to 200 transcript siblings per call (src/chat.ts:158-188), and `flush-tools` blocks every prompt, so an unbounded "scan whenever empty" would pay that cost on most prompts forever. Residue: a straggler PostToolBatch from the predecessor id that arrives after adoption stays in the old-id file - a stale cache file, bounded harm. This reuses `scanPredecessorTranscript` (returns the raw predecessor id) with a **queue-existence predicate** - not `resolveRegisteredPredecessor` as-is, whose predicate is registered chat identity (a predecessor that never used chat has no row, and chat-disabled users must still adopt). The only new surface is an exported `adoptQueue(fromID, toID)` in src/extract-queue.ts (`queuePath`/`safeName` are module-private today). Host-owned and deterministic - no model judgment. Shippable alone; scoped separately so the core change stays reviewable.
4. **Held, with revival conditions:** the `mcp_tool` hook delivery and the headless extractor, in that order of preference. Revive only if inline delivery proves insufficient in practice - models ignoring the injected payload at rates the escalation ladder does not curb. The headless extractor is the stronger successor (it removes model compliance from the loop entirely); the `mcp_tool` variant's costs (version gate, wrapper tool, double-delivery suppression) buy delivery determinism the command hook already provides.

## Acceptance criteria

- A Claude Code extraction cycle completes with **zero sub-agent dispatches**: no Task/Agent/subagent tool call is part of the flow, asserted by tests (the inline nudge text contains no dispatch instruction) and by a QA use case covering the full cycle.
- The loop class is dead by construction: simulating a full inline extraction cycle (buffer -> flush -> process -> ack) leaves the queue empty and generates no new buffer entries from the flow itself; in particular the flow never produces a `SubagentHandback` or a fetch-tool call to re-buffer. The parent's own verifying tool calls during processing may buffer - covered as the bounded re-feed tail in the same QA cycle test.
- Payload delivery respects the 10,000-character cap: instructions first; a queue that would print over the threshold produces instructions + queue-file path instead (unit test with an oversized queue). The host's own over-cap fallback is a second net behind this.
- Escalation is preserved: consecutive ignored nudges escalate tone through the levels with the payload, or its queue-file path over the cap, always delivered; a save or ack resets the counter; the skew gate still pauses extraction without counting.
- Cursor is pinned unchanged: its stage 1 still emits the dispatch nudge, and its AGENTS.md instructions gain no inline wording (existing tests/plugin-prompts.test.ts and tests/setup-cursor.test.ts expectations extended with explicit pins; tests/version-skew.test.ts's stage-1 simulations split per host - the dispatch-wording pins move to Cursor, while the skew gate's tool-naming rationale is unchanged on both hosts, since the inline nudge still names `extraction_done`).
- Docs updated in both tiers with no stale dispatch wording surviving on the Claude Code path (grep sweep for "dispatch"/"sub-agent" in extraction docs after the edit); `mise run check` and `mise run qa-auto` green.

## Blast radius and consumers

- `flush-tools` is shared by Claude Code and Cursor - the host branch and the `src/flush.ts` extraction are the only shared-code changes; Cursor's path is pinned by tests.
- `extractionNudge`/`buildExtractionNudge` are consumed by bin/thatch flush-tools (Cursor after this plan) and directly by two test files that pin the dispatch wording (tests/version-skew.test.ts, tests/plugin-prompts.test.ts) - signatures unchanged; the pins get per-host scoping.
- `get_extraction_payload` keeps all callers: Cursor's extractor and opencode's plugin-created children. Only its description text changes. The skill artifact rework (above) rides the setup auto-refresh sync (src/skills.ts).
- No settings-file schema change, no new hooks, no queue format change: setup.ts, `.claude/settings.json` output, and existing on-disk queues are untouched by step 2. The CLAUDE.md instruction block is rewritten by setup's idempotent auto-refresh on upgrade (src/mcp.ts:236-259), which is the delivery vehicle for the wording change; the skill artifact propagates through the same auto-refresh (artifacts/skills synced by src/skills.ts).
- The queue files themselves: same directory, same shape, same cap; adoption (step 3) renames files, moves the missed count file, and writes a one-attempt `<safeName>.adopted` sentinel.

## Intent breadcrumbs (comments the implementation will write)

- `src/flush.ts` header: why the stages live in src/ (testability; bin/thatch is outside tsconfig) and why host selection is id-field based (one test per host path).
- The inline nudge builder: why payload delivery never degrades to a pointer without a Read instruction (a pointer-stall stalls the queue forever - no fetch tool exists on this host and the queue path is unknown to the model) and why the escalation ladder is shared with the dispatch builder.
- `adoptQueue`: why adoption uses a queue-existence predicate instead of chat registration (chat-disabled users; unregistered predecessors), and why the one-attempt sentinel is correct rather than lazy: the scan is per-prompt cost in a prompt-blocking hook, and a straggler predecessor-id buffer arriving after adoption is a stale cache file, not lost data.
- `extraction_done` docstring: the no-drain-on-ack rationale is dispatch-path-only; the inline parent acking without processing is a hard drain and the nudge wording is the guard.

## Reviewer orientation

The change replaces a model-driven sub-agent handshake with host-owned payload delivery, on one host only. The mechanism is one branch point (flush stage 1 by id field), one new prompt function sharing an existing escalation ladder, a prerequisite extraction of the stage logic into src/ for testability, and a skill-artifact wording update. The queue, its format, setup, and Cursor are untouched. The riskiest surface is the escalation/ack interplay - an unprocessed ack is a hard drain (silent loss), and a pointer-only fallback would stall the queue - review the state matrix against the nudge text first.

## Risks and open questions

- **Ack without processing is a hard drain.** Under inline, `extraction_done` with the session id consumes the queue regardless of whether the model processed the payload (src/mcp.ts:177-181) - the only permanent-loss transition the plan adds (the dispatch world's unprocessed ack left the queue intact, src/extract-queue.ts:88-98). The guard is prompt-level: the nudge and skill wording tie the ack to "after saving, or when nothing was worth saving." Accepted as the same trust level every nudge instruction already runs at; if field evidence shows silent loss, that is a revival-condition input for step 4.
- **Model ignores the injected payload.** Escalation levels bound this, and the payload is always delivered (no deadlock). If field evidence shows ignoring at scale, the held step 4 names the successors in order.
- **Context cost on tool-dense sessions.** Up to 20 interactions x ~500 chars per delivery until processed, plus the re-feed tail from the parent's own verifying calls - and `UserPromptSubmit` fires on background-task completions and cross-session mail too, so a background-heavy session can re-deliver the payload several times per user turn. The 20-cap and the few-KB digest size bound each delivery; the multiplier is accepted and the escalation ladder is the pressure to process.
